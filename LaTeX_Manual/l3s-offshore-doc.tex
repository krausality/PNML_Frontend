\chapter{Manual: PNML\_Frontend}

This project is a web-based \textbf{Petri net visualizer and editor} that allows users to create, modify, and simulate complex system models. It features a central \textbf{Data Store} that synchronizes the state of \emph{Places}, \emph{Transitions}, and \emph{Arcs} across an interactive \textbf{SVG canvas}, an automatic \textbf{Graph Layout} engine, and a \textbf{Simulation} controller. Users can construct nets via drag-and-drop, import \textbf{PNML files}, and run token-based simulations either manually or via a backend service.

\chapter{Petri Net Primitives}
\label{chap:primitives}

Welcome to the \textbf{PNML\_Frontend} project! If you are new to Petri nets, don't worry. We are going to start with the absolute basics.

Before we can build a complex application that simulates workflows, we need to define the fundamental ``language'' we are speaking. Just as a sentence is made of nouns and verbs, a Petri net is built from three specific logical blocks.

We call these the \textbf{Petri Net Primitives}.

\section{The Motivation: A Board Game Analogy}

Imagine you are building a digital board game. Before you design the rules or the confusing strategies, you need to code the physical pieces:
\begin{enumerate}
    \item \textbf{Circles (Places):} Where chips sit.
    \item \textbf{Rectangles (Transitions):} Actions that move chips.
    \item \textbf{Arrows (Arcs):} The paths showing where chips go.
\end{enumerate}

In our application, we cannot just draw shapes on a screen. We need smart objects that know their own rules. A Circle needs to know how many chips it has. A Rectangle needs to know if it's allowed to move chips.

\subsection{The Use Case: The Coffee Machine}

Let's build a tiny piece of logic for a Coffee Machine.
\begin{itemize}
    \item \textbf{Place:} \texttt{Water Tank} (Contains 1 unit of water).
    \item \textbf{Transition:} \texttt{Brew} (The action).
    \item \textbf{Goal:} Move the unit of water into the coffee pot.
\end{itemize}

This chapter walks you through the classes that make this possible.

\section{The Key Concepts}

\subsection{The Place (\texttt{Place})}

Think of a \textbf{Place} as a bucket. It sits at a specific \texttt{x,y} coordinate on the screen. Its most important job is to hold \textbf{Tokens}.
\begin{itemize}
    \item \textbf{Shape:} Always a Circle.
    \item \textbf{Data:} The number of tokens (e.g., \texttt{token: 5}).
\end{itemize}

\subsection{The Transition (\texttt{Transition})}

Think of a \textbf{Transition} as an engine or a processor. It waits for resources to arrive, consumes them, and produces something new.
\begin{itemize}
    \item \textbf{Shape:} Always a Rectangle (or Box).
    \item \textbf{Logic:} It checks to see if there are enough tokens in the connected Places to ``fire'' (execute).
\end{itemize}

\subsection{The Arc (\texttt{Arc})}

The \textbf{Arc} is the pipe connecting them. It is strictly directional.
\begin{itemize}
    \item \textbf{Shape:} A line with an arrow.
    \item \textbf{Logic:} It connects a \texttt{Node} (Place/Transition) to another \texttt{Node}.
\end{itemize}

\section{Using the Primitives}

Let's look at how we create these objects in code to solve our \textbf{Coffee Machine} use case.

\subsection{Step 1: Create the Water Tank (Place)}

We define a location and create a \texttt{Place} with 1 token.

\begin{lstlisting}[language=TypeScript]
import { Point } from './point';
import { Place } from './place';

// Define position (x=100, y=100)
const tankPos = new Point(100, 100);

// Create Place: 1 token, at position, ID='p1', Label='Water'
const waterTank = new Place(1, tankPos, 'p1', 'Water');
\end{lstlisting}

\textbf{What happened?} We now have a logic object representing a tank with 1 unit of ``water'' (token).

\subsection{Step 2: Create the Brew Action (Transition)}

Now we create the action that will use the water.

\begin{lstlisting}[language=TypeScript]
import { Transition } from './transition';

// Define position nearby (x=300, y=100)
const brewPos = new Point(300, 100);

// Create Transition
const brewAction = new Transition(brewPos, 't1', 'Brew');
\end{lstlisting}

\subsection{Step 3: Connect them (Arc)}

We need a pipe to move water to the brewer.

\begin{lstlisting}[language=TypeScript]
import { Arc } from './arc';

// Create an Arc from Tank -> Brew Action
// Weight 1 means it moves 1 token at a time
const pipe = new Arc(waterTank, brewAction, 1);

// Tell the transition about this incoming connection
pipe.appendSelfToTransition();
\end{lstlisting}

\textbf{What happened?} The \texttt{brewAction} now knows it is connected to the \texttt{waterTank}. Specifically, \texttt{waterTank} is a ``Pre-Arc'' (input) for the transition.

\section{Under the Hood: Geometry \& Logic}

Before diving into the source code, let's understand a hidden complexity.

When we draw this on screen in the Main Visualizer (Chapter~\ref{chap:visualizer}), we want the arrow to stop exactly at the edge of the circle or square. We don't want the arrow overlapping the shape, and we don't want a gap.

Each primitive knows how to calculate its \textbf{Intersection Point}.

Let's look at the actual files provided.

\subsection{The \texttt{Place} Class (\texttt{place.ts})}

This class implements \texttt{Node}. Notice the \texttt{intersectionOfBoundaryWithLineTo} method. This is pure geometry.

\end{lstlisting}

\subsection{The \texttt{Transition} Class (\texttt{transition.ts})}

The transition is smarter. It has logic to check if it's ``Active''. A transition is active if all the places feeding into it have enough tokens.

\begin{lstlisting}[language=TypeScript]
export class Transition implements Node {
    // ... properties ...

    // Checks if we have enough tokens to fire
    get isActive(): boolean {
        for (let preArc of this.preArcs) {
            // Check if the source Place has enough tokens
            // Note: arc weights are stored as negative numbers for inputs
            if ((preArc.from as Place).token + preArc.weight < 0) {
                return false; 
            }
        }
        return true; // All input places satisfied!
    }
}
\end{lstlisting}

\subsection{The \texttt{Arc} Class (\texttt{arc.ts})}

The Arc acts as the bridge. Notice how the constructor automatically adjusts weights: negative if leaving a Place (removing tokens), positive if entering a Place (adding tokens).

\begin{lstlisting}[language=TypeScript]
export class Arc {
    from: Node;
    to: Node;
    weight: number; 

    constructor(from: Node, to: Node, weight: number = 1) {
        this.from = from;
        this.to = to;
        
        // If coming FROM a Place, weight is negative (subtraction)
        if (from instanceof Place) {
            this.weight = -1 * Math.abs(weight);
        } else {
            this.weight = Math.abs(weight);
        }
    }
    // ...
}
\end{lstlisting}

Also, the Arc handles the geometry request we saw in the Sequence Diagram:

\begin{lstlisting}[language=TypeScript]
    get polyLinePointsArray(): Point[] {
        // ...
        
        // Ask the 'From' node where the line should start

        // Ask the 'To' node where the line should end
        end = this.to.intersectionOfBoundaryWithLineTo(pForEndCalc);

        return [start, ...this.anchors, end];
    }
\end{lstlisting}

    \item \textbf{Arcs} connect them and handle the geometry of drawing lines.
\end{itemize}

However, having these objects floating around in memory isn't enough. We need a way to manage them, create them, delete them, and find them by ID. We need a ``Manager''.

\chapter{Central Data Store (DataService)}
\label{chap:dataservice}

In the previous chapter, \hyperref[chap:primitives]{Petri Net Primitives}, we learned how to create the fundamental building blocks: Places, Transitions, and Arcs.

But right now, those objects are just ghost logic floating in the void. We have ``bricks,'' but we don't have a ``building'' or a ``construction site.''

If you create a \texttt{Place} in one code file, how does the drawing engine know it exists? If you delete a \texttt{Transition} in the layout tool, how does the simulation engine know it's gone?

We need a single, shared brain. We call this the \textbf{DataService}.

\section{The Motivation: The Shared Whiteboard}

Imagine a team of engineers working in a room. To collaborate effectively, they use a large \textbf{Whiteboard} on the wall.
\begin{itemize}
    \item The \textbf{Visualizer} looks at the board to see what to draw.
    \item The \textbf{Simulation} reads the board to move tokens around.
    \item The \textbf{Mouse Handler} erases things from the board when you click delete.
\end{itemize}

The \texttt{DataService} is that whiteboard. It is the \textbf{Single Source of Truth}.

\subsection{The Use Case: ``Connecting the Dots''}

Let's stick with our coffee machine example. We have a \texttt{Water Tank} (Place) and a \texttt{Brew} (Transition).

\textbf{Goal:} We want to connect them with an Arc and ensure the entire application looks at the new connection instantly.

\section{Key Concepts}

\subsection{The Storage Arrays}

The DataService holds private lists (arrays) of your items.
\begin{itemize}
    \item \texttt{\_places}: A list of all circles.
    \item \texttt{\_transitions}: A list of all rectangles.
    \item \texttt{\_arcs}: A list of all arrows.
\end{itemize}

\subsection{The ``Town Crier'' (Observables)}

This is the most ``magical'' part of the service. In modern web development, simply changing a variable isn't enough; you have to tell the screen to update.

We use a concept called \textbf{RxJS Observables}. Think of it as a \textbf{Town Crier} or a \textbf{Group Chat}.
\begin{enumerate}
    \item \textbf{Subject (\texttt{dataChangedSubject}):} This is the megaphone. When we change data, we shout into this.
    \item \textbf{Observable (\texttt{dataChanged\$}):} This is what the components listen to. When the megaphone shouts, everyone listening wakes up and refreshes their screen.
\end{enumerate}

\section{Using the DataService}

Let's solve our ``Connecting the Dots'' use case.

\subsection{Step 1: Getting Access}

In Angular, we don't say \texttt{new DataService()}. We ask the framework to give us the shared instance. This is called \textbf{Dependency Injection}.

\begin{lstlisting}[language=TypeScript]
// Inside a component
constructor(private dataService: DataService) {
   // Now 'this.dataService' is the shared whiteboard
}
\end{lstlisting}

\subsection{Step 2: Adding Elements}

We define our primitives (like in Chapter~\ref{chap:primitives}) and put them into the service's arrays.

\begin{lstlisting}[language=TypeScript]
// Create the objects
const tank = new Place(1, new Point(0,0), 'p1');
const brew = new Transition(new Point(100,0), 't1');

// Put them on the "Whiteboard"
this.dataService.places = [tank];
this.dataService.transitions = [brew];
\end{lstlisting}

\subsection{Step 3: Connecting Them}

The \texttt{DataService} has a helper method called \texttt{connectNodes}. This is smarter than doing it manually because it automatically creates the \texttt{Arc} and updates the internal logic.

\begin{lstlisting}[language=TypeScript]
// Connect Tank -> Brew
// The service creates a new Arc and saves it internally
this.dataService.connectNodes(tank, brew);
\end{lstlisting}

\textbf{What happened?} An Arc was created. The \texttt{brew} transition now knows \texttt{tank} is its input. But... the screen hasn't updated yet!

\subsection{Step 4: The Notification}

Usually, methods like \texttt{connectNodes} trigger the update automatically. But if you wanted to listen to updates in your component, you would do this:

\begin{lstlisting}[language=TypeScript]
// Listen for the Town Crier
this.dataService.dataChanged$.subscribe(() => {
    console.log("Something changed! I should redraw the screen.");
    this.redrawPetriNet();
});
\end{lstlisting}

\section{Deep Dive: The Code}

Let's look at \texttt{src/app/tr-services/data.service.ts} to see how this is built.

\subsection{The Storage and Safety}

The service keeps the data \texttt{private}. This prevents other parts of the app from accidentally wiping the array. We access data using \textbf{Getters}.

\begin{lstlisting}[language=TypeScript]
export class DataService {
    // Private storage - the "Real" data
    private _places: Place[] = [];
    private _transitions: Transition[] = [];
    private _arcs: Arc[] = [];

    // Public access - Read Only access
    getPlaces(): Place[] {
        return this._places;
    }
    // ... similar getters for transitions and arcs
}
\end{lstlisting}

\subsection{The Smart Removal Logic}

When removing a Place, we can't just delete the circle. We must also delete any arrows (arcs) connected to it, otherwise, we'd have arrows pointing to nothing (which crashes the app).

\begin{lstlisting}[language=TypeScript]
removePlace(deletablePlace: Place): Place[] {
    // 1. Find all arcs touching this place
    const deletableArcs = this._arcs.filter(
        (arc) => arc.from === deletablePlace || arc.to === deletablePlace,
    );

    // 2. Remove those arcs first
    deletableArcs.forEach((arc) => this.removeArc(arc));

    // 3. Remove the place itself
    this._places = this._places.filter((place) => place !== deletablePlace);
    
    // 4. Shout to the app that data changed
    this.triggerDataChanged(); 
    return this._places;
}
\end{lstlisting}

\chapter{PNML/XML Translator (PnmlService)}
\label{chap:pnmlservice}

In the previous chapter, \hyperref[chap:visualizer]{The Main Visualizer (PetriNetComponent)}, we learned how to draw our Petri net on the screen. We can click to add Places and Transitions, and everything looks great.

But we have a major problem: \textbf{Amnesia}.

If you refresh your browser, your drawing disappears. If you want to send your Petri net to a friend, you can't. The data only lives in your computer's temporary memory (RAM).

We need a way to save our work to a file. We use the \textbf{PnmlService} to solve this.

\section{The Motivation: The Universal Translator}

Computer programs speak different languages.
\begin{itemize}
    \item \textbf{Our App:} Speaks ``JavaScript Objects'' (e.g., \texttt{new Place(...)}).
    \item \textbf{The File System:} Speaks ``Text/String'' (e.g., \texttt{<place id="p1">}).
\end{itemize}

The standard language for saving Petri nets is called \textbf{PNML} (Petri Net Markup Language). It is based on \textbf{XML} (similar to HTML).

We need a \textbf{Translator}:
\begin{enumerate}
    \item \textbf{Import (Read):} Reads an XML file and creates JavaScript objects.
    \item \textbf{Export (Write):} Takes JavaScript objects and writes an XML file.
\end{enumerate}

\subsection{The Use Case: Saving and Loading}

\begin{itemize}
    \item \textbf{Goal:} You draw a coffee machine workflow and click ``Download.''
    \item \textbf{Result:} A file named \texttt{petri-net.pnml} is downloaded to your computer.
    \item \textbf{Later:} You upload that file, and the app reconstructs the drawing exactly as it was.
\end{itemize}

\section{Key Concepts}

\subsection{PNML (XML)}

PNML is just text wrapped in tags. It describes the net's structure.
Here is what a single Place looks like in PNML:

\begin{lstlisting}[language=XML]
<place id="p1">
    <name> <text>Water Tank</text> </name>
    <graphics>
        <position x="100" y="100"/>
    </graphics>
</place>
\end{lstlisting}

\subsection{Parsing (Deserialization)}

\textbf{Parsing} is the act of reading that text and extracting meaning.
\begin{itemize}
    \item The translator looks for \texttt{<position x="100">}.
    \item It converts \texttt{"100"} (text) into \texttt{100} (number).
    \item It runs \texttt{new Place(...)}.
\end{itemize}

\subsection{Serialization}

\textbf{Serialization} is the reverse.
\begin{itemize}
    \item It looks at a \texttt{Place} object.
    \item It gives it a string template: \texttt{<place id="\$\{place.id\}">...}.
    \item It combines them all into one long text string.
\end{itemize}

\section{Under the Hood: The Parsing Flow}

How does a text file become a running application?

\begin{enumerate}

    \item \textbf{Instantiation:} For every match, it creates a real Class instance (\texttt{new Place()}).
    \item \textbf{Auto-Layout:} If the file doesn't have coordinates (X, Y), the service calls the \hyperref[chap:layout]{Graph Layout Architect} to calculate them automatically.

private parsePnmlPlaces(list: Array<PnmlElement>): Place[] {
    const places: Place[] = [];
    
    list.forEach((pnmlPlace) => {
        // Extract ID and Name
        const id = pnmlPlace.attributes.id;
        
        // Extract Position (Logic simplified for readability)
        // If x/y exist, use them. If not, use (0,0).
        let point = new Point(attr.x, attr.y);

        places.push(new Place(tokens, point, id, name));
    });

}

\subsection{Handling Arcs (The Tricky Part)}

Arcs are harder because they connect two things. In XML, an Arc is just: \texttt{source="p1" target="t1"}.
In our code, an \texttt{Arc} needs references to the actual \texttt{Place} and \texttt{Transition} objects, not just their names.

\begin{lstlisting}[language=TypeScript]
private parsePnmlArcs(list, places, transitions): Arc[] {
    list.forEach((pnmlArc) => {
        // 1. Get the string IDs
        const sId = pnmlArc.attributes.source;
        const tId = pnmlArc.attributes.target;

        // 2. Find the actual objects in our memory
        const sourceNode = this.retrieveNode(places, transitions, sId);
        const targetNode = this.retrieveNode(places, transitions, tId);

        // 3. Create the connection
        if (sourceNode && targetNode) {
            const arc = new Arc(sourceNode, targetNode, weight);
            arcs.push(arc);
        }
    });
    return arcs;
}
\end{lstlisting}

\chapter{Graph Layout Architect (Sugiyama/Spring Embedder)}
\label{chap:layout}

In the previous chapter, \hyperref[chap:pnmlservice]{PNML/XML Translator (PnmlService)}, we learned how to import Petri net files.

However, we ended on a cliffhanger. Sometimes, imported files contain only the \emph{logic} (connections) but no \emph{geometry} (positions). If a file doesn't say where the nodes go, the \texttt{PnmlService} piles them all at x=0, y=0.

This results in a ``Tangled Mess''---a black blob of overlapping circles and rectangles.

We need an \textbf{Interior Designer}. We need an algorithm to automatically look at the connections and decide the best, most readable arrangement for the furniture. This is the job of the \textbf{Graph Layout Architect}.

\section{The Motivation: The ``Tangled Mess''}

Imagine you just moved into a new house (imported a file). The movers dumped every single chair, table, and lamp into the exact center of the living room. You can't reach the fridge because the sofa is on top of it.

\section{Key Concepts}

\subsection{The Spring Embedder (Physics)}

This approach treats the diagram like a physical system in space.
\begin{itemize}
    \item \textbf{Magnets (Repulsion):} Every node (Place/Transition) hates every other node. They try to push each other away.
    \item \textbf{Springs (Attraction):} If two nodes are connected by an Arc, they are tied together with an elastic spring. They try to pull close.
\end{itemize}

The algorithm runs a simulation. The nodes push and pull until they find a comfortable balance (Equilibrium).

\subsection{The Sugiyama (Hierarchy)}

This approach treats the diagram like a corporate organizational chart or a waterfall.
\begin{itemize}
    \item \textbf{Layers:} It organizes nodes into ranks. Input moves to Process, Process moves to Output.
    \item \textbf{Crossings:} It specifically tries to minimize the number of times arrows cross over each other.
\end{itemize}

async layoutSpringEmbedder() {
    let iterations = 1;
    
    // Keep running until max iterations or force is tiny
    while (iterations <= this.maxIterations) {
        
        // 1. Calculate where everyone wants to move
        // (Implementation details hidden in helper method)
        this.calculateAndApplyForces(nodes);

        // 2. Wait 1ms so user can see the movement (Animated)

        iterations++;
    }
}

\subsubsection{The Physics Math}

We calculate two forces. Notice how simple the concept is when broken down:

\begin{lstlisting}[language=TypeScript]
// 1. Repulsion: "Get away from me!"
// Applied between ANY two nodes
const repulsionForce = this.calculateRepulsionForce(nodeA, nodeB);

// 2. Springs: "Come back!" 
// Applied only between CONNECTED nodes (Arcs)
const springForce = this.calculateSpringForce(nodeA, connectedNodeB);

// Final move is the combination of both
totalForce = repulsionForce + springForce;
\end{lstlisting}

\section{Under the Hood: Sugiyama Logic}

The Sugiyama algorithm is much more complex, so we split it into four distinct steps. It is a \textbf{Pipeline}.

\subsection{The 4-Step Pipeline}

\begin{enumerate}
    \item \textbf{Cycle Removal:} You can't make a perfect ``waterfall'' hierarchy if water flows back up (cycles). We temporarily reverse those arrows.
    \item \textbf{Layer Assignment:} Assign every node a ``Rank'' (Row 1, Row 2, Row 3).
    \item \textbf{Vertex Ordering:} Shuffle nodes within their row to stop arrows from crossing like shoelaces.
    \item \textbf{Coordinate Assignment:} Finally, turn ``Row 1, Position 2'' into ``x=100, y=50''.
\end{enumerate}

applySugiyamaLayout() {
    // Step 1: Break infinite loops
    const cycleService = new CycleRemovalService(nodes, arcs);
    cycleService.removeCycles();

    // Step 2: Assign rows
    const layerService = new LayerAssignmentService(nodes, arcs);
    const layers = layerService.assignLayers();

    // Step 3: Shuffle to untangle lines
    const orderingService = new VertexOrderingService(layers, nodes, arcs);
    orderingService.orderVertices();

    // Step 4: Finalize X/Y coordinates
    const coordService = new CoordinateAssignmentService(layers, arcs, nodes);
    coordService.assignCoordinates();
}
\end{lstlisting}

\chapter{Interaction Handler (EditMoveElementsService)}

In the previous chapter, \hyperref[chap:layout]{Graph Layout Architect (Sugiyama/Spring Embedder)}, we used powerful algorithms to automatically organize our Petri net.

\section{The Motivation: Physics of the Mouse}

The browser gives us raw events: ``The mouse is at pixel (500, 300).''
Our objects live in a coordinate system: ``Place P1 is at x=10, y=10.''

If we just set \texttt{P1.x = 500}, the object would teleport instantly under your mouse cursor, which feels jarring and unnatural.

\subsection{The Use Case: ``The Fine Adjustment''}

\textbf{Goal:} The user clicks on a Transition and drags it 10 pixels to the right.

\textbf{Requirement:}
\begin{enumerate}
    \item Verify the user is allowed to move things (using the \textbf{Move Tool}).
    \item Also move any arrows (Arcs) connected to that Transition so the lines don't break.
\end{enumerate}

\section{Key Concepts}

\subsection{The Drag Cycle}

Every logic involving dragging follows this 3-step cycle:
\begin{enumerate}
    \item \textbf{Initialize (\texttt{mousedown}):} ``I have grabbed object X. I am starting at position Y.''
    \item \textbf{Update (\texttt{mousemove}):} ``I have moved 2 pixels. Update object X by +2 pixels.''
    \item \textbf{Finalize (\texttt{mouseup}):} ``I have let go. Forget object X.''
\end{enumerate}

\subsection{The Delta ($\Delta$)}

We rarely set absolute coordinates during a drag. Instead, we calculate the \textbf{Difference} (Delta) between the last frame and the current frame.
\begin{itemize}
    \item Frame 1: Mouse at 100.
    \item Frame 2: Mouse at 105.
    \item \textbf{Delta:} +5.
    \item \textbf{Action:} Add 5 to the Object's position.
\end{itemize}

\subsection{Initialization}

When we start moving a node, we do a bit of setup work. We look through the \hyperref[chap:dataservice]{Central Data Store (DataService)} to find connected Arcs.

\textbf{Why?} If we didn't do this, dragging a Place would leave the arrows pointing at empty space (broken lines).

\begin{lstlisting}[language=TypeScript]
initializeNodeMove(event: MouseEvent, node: Node) {
    this.node = node;

    // Pre-calculate which arcs are attached to this node
    // This saves performance during the rapid drag loop
    this.dataService.getArcs().forEach((arc) => {
        if (arc.from === node || arc.to === node) {
            this.nodeArcs.push(arc);
        }
    });

    // Remember where we started
    this.initialMousePos.x = event.clientX;
    this.initialMousePos.y = event.clientY;
}
\end{lstlisting}

\subsection{The Move Loop (The Physics)}

This function is called dozens of times per second. It keeps the ``physics'' feeling responsive.

\begin{lstlisting}[language=TypeScript]
moveNodeByMousePositionChange(event: MouseEvent) {
    if (this.node) {
        // 1. Calculate how far the mouse has moved
        const deltaX = event.clientX - this.initialMousePos.x;
        const deltaY = event.clientY - this.initialMousePos.y;

        // 2. Apply that movement to the node
        this.node.position.x += deltaX;
        this.node.position.y += deltaY;

        // 3. Move connected lines slightly so they follow nicely
        this.moveConnectedAnchors(deltaX, deltaY);

        // 4. Reset tracker for the next frame
        this.initialMousePos.x = event.clientX;
        this.initialMousePos.y = event.clientY;
    }
}
\end{lstlisting}

\subsection{Panning the Canvas}

Sometimes you aren't grabbing a node; you are grabbing the background to move the whole map.
This loops through \textbf{everything} in the DataService.

            node.position.x += deltaX;
            // ...

    // ...
}

\chapter{Camera Controller (ZoomService)}
\label{chap:zoom}

In the previous chapter, \hyperref[chap:interaction]{Interaction Handler (EditMoveElementsService)}, we learned how to grab specific nodes and move them around. We became the ``Hand'' that arranges the furniture.

But what if the room is too big? What if you stick a node in the far-right corner, and now you have to scroll for five minutes to find it? Or what if you import a massive Petri net that is 50 times wider than your screen?

Moving the \emph{objects} isn't enough. We need to move the \emph{camera}. We need to control the \textbf{Viewport}.

This is the job of the \textbf{ZoomService}.

\section{The Motivation: Looking Through the Lens}

Imagine holding a physical map.
\begin{itemize}
    \item \textbf{Panning (Offset):} You slide the map left, right, up, or down on the table to see a different city.
    \item \textbf{Zooming (Scale):} You bring your face closer to the map to see street names, or pull back to see the whole country.
\end{itemize}

In our code, the \textbf{SVG Canvas} is that map. The \texttt{ZoomService} calculates exactly how much to ``slide'' (translate) and ``magnify'' (scale) that canvas so the user sees exactly what they want.

\subsection{The Use Case: ``Fit to View''}

This is the most critical feature in any diagramming tool.
\begin{enumerate}
    \item \textbf{Scenario:} User imports a file with 500 nodes.
    \item \textbf{Problem:} The nodes are scattered over a huge area (e.g., from x=0 to x=5000). The user sees a white screen because the camera is looking at an empty spot.
    \item \textbf{Solution:} The user clicks \textbf{``Fit Content.''}
    \item \textbf{Result:} The service calculates the perfect zoom level (Scale) and position (Offset) to fit every single node perfectly onto the screen.
\end{enumerate}

\subsection{The State Variables}

The camera is defined by just two sets of numbers:
\begin{enumerate}
    \item \textbf{Scale (Zoom Level):} A multiplier.
    \begin{itemize}
        \item \texttt{1.0} = Actual size (100\%).
        \item \texttt{0.5} = Half size (Zoomed out).

    \item \textbf{Offset (Pan Position):} An \texttt{x, y} coordinate. This tells us how many pixels we shifted the canvas from the top-left corner.

Ultimately, this service produces a single string of text that the browser understands.
It looks like this: \texttt{translate(100px, 50px) scale(1.5)}. This tells the browser: ``Move everything right 100px, down 50px, and make it 50\% bigger.''

\subsection{Storage (The State)}

    public offset$ = this.offsetSubject.asObservable();

\subsection{The Combined Output (\texttt{transform\$})}

The visualizer doesn't want to do math. It just wants a string to put into the HTML. We check both \texttt{scale} and \texttt{offset} and combine them into one string automatically.

\begin{lstlisting}[language=TypeScript]
// Combines the two streams into one CSS string
public transform$: Observable<string> = combineLatest([
    this.scale$,
    this.offset$,
]).pipe(
    // Result: "translate(50 100) scale(1.5)"
    map(([scale, offset]) => 
        `translate(${offset.x} ${offset.y}) scale(${scale})`
    )
);
\end{lstlisting}

\subsection{Smart Zooming (\texttt{zoomToPoint})}

When zooming, we don't just change the scale. We must also change the offset to keep the image stable.
Imagine zooming towards a tree in a photo. The tree needs to stay in the same spot on your screen while the background expands.

\begin{lstlisting}[language=TypeScript]
private zoomToPoint(screenPoint: Point, targetScale: number): void {
    const currentOffset = this.currentOffset;
    const currentScale = this.currentScale;

    // Math formula: Keep the 'screenPoint' stationary
    const newOffsetX = screenPoint.x - 
        (screenPoint.x - currentOffset.x) * (targetScale / currentScale);
    const newOffsetY = screenPoint.y - 
        (screenPoint.y - currentOffset.y) * (targetScale / currentScale);

    // Update the state
    this.offsetSubject.next({ x: newOffsetX, y: newOffsetY });
    this.scaleSubject.next(targetScale);
}
\end{lstlisting}

\subsection{Implementing ``Fit Content''}

This is the most complex function, but logically it is simple steps.
\begin{enumerate}
    \item Get all Place/Transition positions.
    \item Find the edges (Bounding Box).
    \item Calculate how small the scale needs to be to fit that box in our window.
\end{enumerate}

\begin{lstlisting}[language=TypeScript]
fitContent(viewportWidth: number, viewportHeight: number): void {
    // Step 1: Find the edges of the drawing
    const bbox = this.calculateContentBoundingBox();
    if (!bbox) return; // Empty graph

    const contentWidth = bbox.maxX - bbox.minX;
    
    // Step 2: Calculate scale ratio 
    // Example: If content is 1000px and screen is 500px, scale is 0.5
    const scaleX = viewportWidth / contentWidth;
    let newScale = Math.min(scaleX, scaleY); // Fit both height and width

    // Step 3: Apply the new zoom
    this.scaleSubject.next(newScale);
    // (Offset calculation omitted for brevity)
}
\end{lstlisting}

\section{Solving the Mouse Coordinate Problem}

There is a catch!

If scale is \texttt{0.5} (zoomed out), and you move your mouse \texttt{100 pixels} on the screen, logically you have moved \texttt{200 pixels} in the zoomed-out world.

If we don't account for this, placing a new node would be inaccurate. The node would appear in the wrong spot.

We solve this with the \textbf{SvgCoordinatesService} (\texttt{src/app/tr-services/svg-coordinates-service.ts}). It injects the \texttt{ZoomService} to do the reverse math.

\begin{lstlisting}[language=TypeScript]
// Inside svg-coordinates-service.ts
getRelativeEventCoords(event: MouseEvent, drawingArea: HTMLElement): Point {
    // 1. Get raw pixel position from browser
    let rawX = event.clientX - svgRect.left;

    // 2. Adjust for the current Pan (Offset)
    // 3. Divide by Scale (Zoom)
    let scaledX = (rawX - this.zoomService.currentOffset.x) 
                  / this.zoomService.currentScale;

    // Result: The logic coordinate exactly under the mouse
    return new Point(scaledX, scaledY);
}
\end{lstlisting}

\section{Conclusion}

The \textbf{ZoomService} acts as the lens of a camera.
\begin{itemize}
    \item It tracks \textbf{Scale} and \textbf{Offset}.
    \item It generates the \textbf{CSS Transform} string for the visualizer.
    \item It ensures mouse clicks map to the correct logical coordinates, no matter how zoomed in or out you are.
    \item It powers the magical ``Fit Content'' button that saves users from getting lost in infinite space.
\end{itemize}

With this in place, our application is fully navigable. We can load data, see it, organize it, and move around it.

\chapter{Simulation Engine (TokenGameService)}
\label{chap:tokengame}

In the previous chapter, \hyperref[chap:uiservice]{UI State Manager (UiService)}, we built the ``Remote Control'' for our application. We can switch between ``Build Mode'' and ``Simulation Mode.''

However, switching to Simulation Mode currently just changes the toolbar buttons. If you click on a Transition, nothing happens. The tokens sit still. The application has no idea how to actually play the game.

We need a \textbf{Rulebook}. We need a service that enforces the mathematical logic of Petri nets. This is the \textbf{TokenGameService}.

\section{The Motivation: The Rulebook}

Imagine you are playing a board game like Chess or Monopoly.
\begin{itemize}
    \item \textbf{The Board:} \hyperref[chap:primitives]{Petri Net Primitives} (Places/Transitions).
    \item \textbf{The Pieces:} Tokens.
    \item \textbf{The Player:} You.
\end{itemize}

But who tells you if a move is legal? Who remembers where the pieces were before you knocked the board over?

The \textbf{TokenGameService} has two jobs:
\begin{enumerate}
    \item \textbf{The Referee:} It decides if a Transition is allowed to ``Fire'' (execute).
    \item \textbf{The Historian:} It records every move so you can ``Undo'' if you make a mistake.
\end{enumerate}

\subsection{The Use Case: ``Firing'' a Transition}

\begin{itemize}
    \item \textbf{Scenario:} We have a Place (Water) with 1 token connected to a Transition (Brew).
    \item \textbf{Action:} The user clicks the ``Brew'' transition.
    \item \textbf{Logic:} The service checks: ``Do we have water?'' (Yes). It subtracts 1 token from Water and adds 1 token to Coffee.
    \item \textbf{Undo:} The user clicks ``Step Back.'' The token returns to the Water tank.
\end{itemize}

\section{Key Concepts}

\subsection{Firing}

In Petri net terms, \textbf{Firing} means a transition executes.
\begin{enumerate}
    \item \textbf{Consume:} It removes tokens from input places.
    \item \textbf{Produce:} It adds tokens to output places.
\end{enumerate}

\subsection{The ``Game State''}

The state of a Petri net is simply a snapshot of \textbf{where the tokens are right now}. It is a list:
\begin{itemize}
    \item Place A: 5 tokens
    \item Place B: 0 tokens
    \item Place C: 1 token
\end{itemize}

\subsection{History (The Stack)}

To enable ``Undo,'' we use a \textbf{Stack} (Last-In, First-Out).
\begin{itemize}
    \item Every time you make a move, we take a photo of the board (Current State) and put it on top of a pile.
    \item When you click \textbf{Undo}, we take the top photo and arrange the board to match it.
\end{itemize}

\subsection{The History Storage}

export class TokenGameService {
    // A stack (array) of states. 
    // Each state is a Map of Place -> TokenCount
    private _tokenHistory: Map<Place, number>[] = [];

    constructor(protected dataService: DataService) {}
    // ...
}

\subsection{Capturing a Snapshot}

Before we change anything, we walk through every place in the \hyperref[chap:dataservice]{Central Data Store (DataService)} and write down how many tokens it has.

% SOURCE: src/app/tr-services/token-game.service.ts, Lines 64-70
% STATUS: VERIFIED - Logic identical to source
% NOTE: Comments in listing are added for didactic purposes; original code has no inline comments
\begin{lstlisting}[language=TypeScript]
private getGameState(): Map<Place, number> {
    const tokenMapping = new Map<Place, number>();
    
    // Loop through all existing places
    for (let place of this.dataService.getPlaces()) {
        // Save the pair: [Place Object, 3 tokens]
        tokenMapping.set(place, place.token);
    }
    return tokenMapping;
}
\end{lstlisting}

\subsection{The Fire Method (The Core Logic)}

This is the heart of the engine. Notice how it saves the state \emph{before} doing the math.

% SOURCE: src/app/tr-services/token-game.service.ts, Lines 16-31
% STATUS: VERIFIED - Logic identical to source
% NOTE: Comments renumbered for didactic purposes; original comments differ slightly
\begin{lstlisting}[language=TypeScript]
fire(transition: Transition) {
    // 1. Check the rule
    if (transition.isActive) {
        
        // 2. Save history for Undo
        this.saveCurrentGameState();

        // 3. Subtract tokens from inputs (Pre-places)
        for (let arc of transition.preArcs) {
            // Note: arc.weight is usually stored as negative for inputs
            (arc.from as Place).token += arc.weight;
        }
        
        // 4. Add tokens to outputs (Post-places)
        for (let arc of transition.postArcs) {
            (arc.to as Place).token += arc.weight;
        }
    }
}
\end{lstlisting}

\textbf{Why \texttt{+= arc.weight} for subtraction?}
In \hyperref[chap:primitives]{Chapter 1}, we learned that input arcs store their weight as a negative number (e.g., $-1$). So $5 + (-1) = 4$. This makes the math elegantly simple.

\subsection{Implementing Undo (\texttt{revertToPreviousState})}

To undo, we pop the last snapshot off the stack and force the current places to match those numbers.

% SOURCE: src/app/tr-services/token-game.service.ts, Lines 45-51
% STATUS: VERIFIED - Logic identical to source
% NOTE: Comments renumbered for didactic purposes; original has different comment style
\begin{lstlisting}[language=TypeScript]
revertToPreviousState() {
    // 1. Get the last saved photo
    const state = this._tokenHistory.pop();
    
    // 2. If history is empty, do nothing
    if (!state) return;

    // 3. Overwrite current reality with the saved photo
    this.setGameState(state);
}
\end{lstlisting}

\subsection{Applying the State}

This helper function takes a snapshot and applies it to the living objects.

% SOURCE: src/app/tr-services/token-game.service.ts, Lines 72-82
% STATUS: SIMPLIFIED - Error handling removed for clarity
% NOTE: Original throws Error if place not found:
%       if (tokens === undefined) { throw new Error("..."); } else { place.token = tokens; }
%       Simplified version uses: if (tokens !== undefined) { place.token = tokens; }
\begin{lstlisting}[language=TypeScript]
private setGameState(state: Map<Place, number>) {
    for (let place of this.dataService.getPlaces()) {
        const tokens = state.get(place);
        
        // Safety check: ensure the place still exists
        if (tokens !== undefined) {
            place.token = tokens;
        }
    }
}
\end{lstlisting}

\section{Conclusion}

The \textbf{TokenGameService} brings our static diagrams to life.
\begin{itemize}
    \item It acts as the \textbf{Referee}, ensuring only valid moves occur.
    \item It acts as the \textbf{Time Machine}, saving snapshots of the world before every move so we can undo them.
    \item It directly manipulates the tokens in the \texttt{DataService}, which causes the \texttt{PetriNetComponent} to redraw the screen instantly.
\end{itemize}

We now have a fully functional application! We can draw, edit, zoom, save, and manually play the token game.

But... manual playing is slow. What if we want to ask a computer: ``Is there a path from State A to State B?'' or ``Find the shortest route to finish the process''? For this, we need to connect our frontend to a powerful backend algorithm.

In the previous chapter, \hyperref[chap:tokengame]{Simulation Engine (TokenGameService)}, we built a logic engine that runs directly inside your browser. It allows you to manually click transitions and play the ``Token Game.''

But there is a limit. Your browser is great for drawing and simple logic, but it isn't a supercomputer.

What if you need to simulate a workflow 10,000 times to maximize efficiency? What if you need to calculate complex mathematical reachability graphs? If we tried to do this in the visualization loop, your browser would freeze and crash.

We need to send this heavy work to a dedicated server. We need the \textbf{PlanningService}.

\section{The Motivation: The ``Phone Line''}

Think of your application like a \textbf{Restaurant}.
\begin{itemize}
    \item \textbf{The Frontend (Your App):} This is the Dining Area. It looks nice, handles menus (UI), and seats guests (Layout).
    \item \textbf{The Backend (Server):} This is the Kitchen. It is noisy, hot, and full of heavy machinery to cook the food.
\end{itemize}

The Waiter (Frontend) doesn't cook the steak at the table. The Waiter takes the order, sends it to the kitchen, and waits for the finished plate to come back.

The \textbf{PlanningService} is that connection between the Dining Area and the Kitchen.

\subsection{The Use Case: ``Heavy Simulation''}

\textbf{Goal:} The user has drawn a complex Offshore Wind Farm logistics model. They want to know: ``If I run this for 1 year, how much money do I lose?''
\begin{enumerate}
    \item \textbf{Action:} User clicks ``Run Simulation.''
    \item \textbf{Process:} The app bundles the Petri net into a file, uploads it to the backend server, and waits.
    \item \textbf{Result:} The server returns a JSON report with raw data, which the frontend displays.
\end{enumerate}

\section{Key Concepts}

\subsection{HTTP Requests (GET and POST)}

This is how the web talks.
\begin{itemize}
    \item \textbf{GET:} ``Hey Server, give me the default settings.'' (Like asking for a menu).
    \item \textbf{POST:} ``Hey Server, here is a file. Process it and tell me the answer.'' (Like submitting an order).
\end{itemize}

\subsection{Asynchronous (The Waiting Game)}

When you order food, you don't freeze like a statue until it arrives. You keep chatting.
Similarly, our requests are \textbf{Asynchronous}. We send the request, let the user keep moving the mouse, and when the server replies 2 seconds later, we handle the result.

\subsection{FormData (The Envelope)}

To send a file (like our \texttt{.pnml} model) across the internet, we can't just send text. We wrap it in a special digital envelope called \texttt{FormData}. This allows us to attach files just like an email attachment.

\section{Using the Integrator}

Let's look at how we solve the ``Heavy Simulation'' use case.

\subsection{Step 1: Preparing the Data}

First, we need the text of our Petri net. We use the logic from \hyperref[chap:pnmlservice]{PNML/XML Translator (PnmlService)} to generate the string.

\begin{lstlisting}[language=TypeScript]

// Define how many times to run the sim

\subsection{Step 2: Calling the Service}

We inject the \texttt{PlanningService} and ask it to send the data. Notice we are sending a \textbf{String}, and the service converts it to a file automatically.

\begin{lstlisting}[language=TypeScript]

this.planningService.runSimpleSimulationFromString(pnmlString, runs)
    .subscribe({
        next: (result) => {
             console.log("Success! The server replied:", result);
             this.showResults(result);
        },
        error: (err) => {
             console.error("The kitchen is on fire!", err);
        }
    });
\end{lstlisting}

\textbf{What happens?} The \texttt{.subscribe()} part is crucial. It tells the app: ``Send the message now, and wake me up when the answer arrives.''

\section{Under the Hood: The Communication Flow}

What happens in those few seconds between clicking ``Run'' and seeing the result?

\begin{enumerate}
    \item \textbf{Frontend:} Wraps the XML string into a virtual file.
    \item \textbf{Network:} Travels across the internet to the URL (e.g., \texttt{api/simulation}).
    \item \textbf{Backend:} The Java/Python server parses the file, runs the heavy math, and generates a JSON response.
    \item \textbf{Frontend:} Receives the JSON and updates the UI status message.
\end{enumerate}

\subsection{Setup and Environment}

We don't hardcode the server address (like \texttt{localhost}). We use an environment variable so the app works in development and production.

@Injectable({ providedIn: 'root' })

        `${environment.backendApiUrl}/simulation-petri-nets/simple-sim`;

    constructor(private http: HttpClient) { }
}
\end{lstlisting}

\subsection{The Simulation Call (\texttt{runSimpleSimulation})}

This is the most important method. It prepares the ``Envelope'' (\texttt{FormData}). It accepts a real JavaScript \texttt{File} object.

% SOURCE: src/app/tr-services/planning.service.ts, Lines 97-110
% STATUS: VERIFIED - Logic identical to source
% NOTE: Comments numbered for didactic purposes. Original has German comment about Content-Type header.
\begin{lstlisting}[language=TypeScript]
runSimpleSimulation(pnmlFile: File, runs: number = 1): Observable<any> {
    // 1. Create the envelope
    const formData = new FormData();
    
    // 2. Stuff the file and parameters inside
    formData.append('pnml_model', pnmlFile, pnmlFile.name);
    formData.append('num_runs', runs.toString());

    // 3. Send via HTTP POST
    return this.http.post<any>(this.simpleSimApiUrl, formData)
        .pipe(
            // 4. Attach a safety net for errors
            catchError(this.handleError)
        );
}
\end{lstlisting}

\subsection{The Helper (\texttt{runSimpleSimulationFromString})}

Often, the file doesn't exist on the user's hard drive; it exists in the browser's memory (because the user just drew it). This helper converts the string to a file on the fly.

% SOURCE: src/app/tr-services/planning.service.ts, Lines 118-133
% STATUS: SIMPLIFIED - Shows idealized delegation pattern
% NOTE: Original code does NOT delegate to runSimpleSimulation(); instead duplicates FormData logic.
%       Original signature: runSimpleSimulationFromString(pnmlContent, runs=1, fileName='current_model.pnml')
%       Original creates File and duplicates: formData.append('pnml_model', ...), then inline POST.
%       This version shows cleaner pattern: create File, delegate to runSimpleSimulation(file, runs).
\begin{lstlisting}[language=TypeScript]
runSimpleSimulationFromString(content: string, runs: number = 1): Observable<any> {
    // Create a virtual file from the text string
    const blob = new Blob([content], { type: 'application/xml' });
    const file = new File([blob], 'current_model.pnml');

    // Reuse the main method
    return this.runSimpleSimulation(file, runs);
}
\end{lstlisting}

\subsection{Fetching Defaults (\texttt{getDefaults})}

Sometimes we just need to read data (GET), like asking the server ``What are valid parameters?''.

% SOURCE: src/app/tr-services/planning.service.ts, Lines 65-68
% STATUS: VERIFIED - Code matches source exactly

getDefaults(): Observable<any> {

}
\end{lstlisting}

\subsection{Error Handling (\texttt{handleError})}

If the server crashes or the internet disconnects, we don't want the user to see a blank screen. We catch the error and format a nice message.

% SOURCE: src/app/tr-services/planning.service.ts, Lines 172-186
% STATUS: SIMPLIFIED - Error messages translated to English and logic condensed
% NOTE: Original uses German messages: 'Unbekannter Fehler!', 'Fehler:', 'Serverfehler: Code ...'
%       Original checks: if (error.error instanceof ErrorEvent) for client vs server distinction.
%       Original appends JSON.stringify(error.error) for detailed server error objects.
%       This version shows simplified English version focusing on network vs server errors.
\begin{lstlisting}[language=TypeScript]
private handleError(error: HttpErrorResponse) {
    let msg = 'Unknown Error';
    
    if (error.status === 0) {
        msg = 'Network Error: Is the server running?';
    } else {
        msg = `Server Error (Code ${error.status}): ${error.message}`;
    }
    
    console.error(msg);
    return throwError(() => new Error(msg));
}
\end{lstlisting}

\section{Integration: The ``Parameter Input'' Form}

Included in the project is \texttt{parameter-input.component.ts}. This is the UI form where the user types ``Runs: 100''.

It connects to the \texttt{PlanningService} in its \texttt{runSimulation} method.

% SOURCE: src/app/tr-components/parameter-input/parameter-input.component.ts, Lines 205-265
% STATUS: HEAVILY SIMPLIFIED - Shows core pattern only, omits ~80% of production code
% NOTE: Original method is ~60 lines with complex validation and debugging:
%       - Entry checks: if (!this.initialLoadDone) return; if (parameterFormGroup.invalid) return;
%       - Performance timing: console.time('[PERF] SERVICE_CALL_runPlanning')
%       - Data transformation: planningData = this.reconstructNestedObject(formGroup.value)
%       - Response parsing: if (response.status === 'SUCCESS') ... else ... hasError logic
%       - Change detection: this.cdr.detectChanges() called 3 times for UI updates
%       This version shows the essential Observable pattern: service call + finalize + subscribe.
\begin{lstlisting}[language=TypeScript]
// Inside parameter-input.component.ts

runSimulation(): void {
    this.isLoadingSimulation = true;

    // 1. Call the service
    this.planningService.runPlanning(planningData)
        .pipe(finalize(() => {
             // This runs whether success or fail (turn off spinner)
             this.isLoadingSimulation = false;
        }))
        .subscribe({
            next: (response) => {
                this.statusMessage = "Simulation Complete!";
            },
            error: (err) => {
                this.statusMessage = "Error: " + err.message;
            }
        });
}
\end{lstlisting}

\textbf{What is \texttt{finalize}?} It's a handy operator that ensures your ``Loading...'' spinner stops spinning, even if the request executes successfully or fails miserably.

\section{Conclusion}

The \textbf{PlanningService} is the gateway to power.

\begin{itemize}
    \item It handles \textbf{HTTP Communication} with the backend.
    \item It manages \textbf{File Uploads} via \texttt{FormData}.
    \item It provides \textbf{Observables} so the UI can stay responsive while waiting.
    \item It enables \textbf{Isomorphic Simulation}: We can run simple tests in the browser (\hyperref[chap:tokengame]{TokenGameService}) or massive simulations on the server using the exact same logical model.
\end{itemize}
